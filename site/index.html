    Engine Adapters · bin/claivelib/engines/

    Five harnesses, one contract—without lowest-common-denominator compromises.

    Each adapter is a thin hook tuned to its harness's real CLI and streaming protocol. Unified config keys in ~/.config/claive/config.yaml (or JSON) and per-launch --set overrides govern models, efforts, and providers across every engine.

    What claive is

    An outer control plane for process lifecycles, isolated Git worktrees, cross-agent messaging, structured progress signals, verification/acceptance gates, and terminal triage. Any agent that can run a shell command or speak MCP can drive it.

    What claive is not

    Not a replacement coding agent and not a restricted sandbox that strips tools. Workers keep their native toolsets, MCP servers, prompt caching, Skillshare skills, and repo instruction files (AGENTS.md, CLAUDE.md, GEMINI.md).

    The Whole Platform

    Everything needed to delegate, observe, verify, and integrate real work.

    Start with a single reusable worker or coordinate parallel multi-model specialists across worktrees, MCP, and unattended server queues.

    Managed Git worktrees & acceptance gates

    Run writers on isolated claive/<id> branches with optional --carry-dirty and --link-deps. Process trees stay contained under systemd-run --user --scope + subreaper, and apply --dry-run enforces verification and ownership gates before merging.

    05 · Verified Arbiter

    Deterministic test-gated refinement

    claive-orch is plain code—not an LLM—that steps workers through L0 direct execution, L1 cross-family critique and repair with automatic git reset on regressions, and L2 selective breadth only when refining stalls.

    claive-orch initnextreportintegrate
    06 · Unattended Queue

    Durable server runner via systemd

    When no parent session is open, claive serve works a durable $CLAIVE_DIR/goals/ queue with wall-clock budgets, workspace allowlists, provider backoff, parked-question inbox events, and a clean stop switch.

    claive goal addgoal answerclaive serveclaive-serve.service

    Verified Orchestration · claive-orch

    Models propose. Plain code and your tests decide.

    For verifier-gated coding tasks, claive-orch climbs a deterministic three-rung ladder and stops the moment your test command passes. Worse attempts are reverted automatically and shelved under a Git ref for inspection.

    1. Direct

      L0

      One worker implements the task in an isolated lane and your verifier command runs. If the checks pass, the run completes immediately without extra spend.

    2. Cross-Family Refine

      L1

      On failure, a read-only critic from a different model family names concrete defects. The same worker session fixes them. Better or equal scores checkpoint; regressions revert via Git and stay under refs/claive-orch/<run>/<lane>/rejected-rN.

    3. Selective Breadth

      L2

      Only after refining stalls (two rounds without improvement, including reverts) does arm D launch a deliberately different second lane in its own worktree. Your verifier picks the winner—never a guess.

    Parent
    Claude Code, Codex, Pi, AGY, or a shell script delegating tasks.
    Worker
    Reusable session writing code inside a workspace or isolated worktree.
    Critic
    Read-only reviewer from a distinct model family naming exact defects.
    Verifier
    Your own test/check command—the sole source of truth for keeping changes.
    Arbiter
    claive-orch: plain Python state machine enforcing one legal step at a time.

    Note on benchmarking: the earlier TTC benchmark experiment is intentionally deferred (see docs/experiment/README.md). claive-orch remains available as an everyday verifier-gated workflow, and this page makes no unverified benchmark or win-rate claims.

    Quickstart

    Up and running in two minutes.

    Requires Linux and Python 3 (standard library only), plus whichever coding harness CLI(s) you already use. Add Cargo to compile the optional native Ratatui dashboard.

    Scope & Honest Limits

    What to know before adopting claive.

    • Linux-first process containment: Designed for Linux (including WSL2) using systemd-run --user --scope, /proc liveness checks, and inotify. macOS and native Windows are not supported targets.
    • Soft vs. enforced read-only: Codex and Muse enforce read-only at the harness level; Pi, Claude Code, and AGY use soft-read instructions unless you require strict enforcement via --require-read-only.
    • Engine binaries are installed separately: Claive wraps the CLIs you already authenticate and pay for (codex, claude, pi, agy, muse). Free-tier routes on Pi can rate-limit or change availability.
    • No fabricated benchmarks: No win-rate or cost-savings claims are published here; the TTC research experiment is deferred until a settled corpus and protocol are explicitly resumed.
