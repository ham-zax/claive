One shot is a bad deal either way

An agent normally gets a single attempt. Easy work is over-served with expensive reasoning. Hard work gets one try that can lock in a bad approach, with nobody checking it.

claive adds the checking, and spends more effort only when the tests show it is needed.

How it works

Work climbs a ladder, and stops as soon as your tests pass.

  1. DirectL0

    One worker tries the job and your test command runs. If it passes, that is the end.

  2. RefineL1

    If it fails, a critic names concrete defects and the same worker session fixes them. Tests run again. A better or equal score is kept as a commit. A worse score is reverted with git, and the rejected attempt stays under a ref so you can inspect it. Two rounds by default, three at most.

  3. BreadthL2

    Only if refining stalls, meaning two rounds without improvement, one deliberately different second attempt runs in a separate git worktree. The tests pick the winner. A run that never passes is reported as stalled or unresolved, never as success.

Parent
The agent you talk to: Claude Code, Codex, a Pi agent, or a shell script. It hands out the jobs.
Worker
A cheaper agent that does the coding.
Critic
A second worker, from a different model family. It reads the result and names defects. It cannot edit.
Verifier
Your test command. Its score is the only thing that counts.
Arbiter
claive-orch. Plain code, not a model. It names one legal next step at a time and refuses commands out of sequence.

Why it's different

  • Your tests are the referee, not another AI's opinion.The critic proposes. Only the test score decides whether a change is kept.
  • Fix before re-roll. Refine an attempt before paying for a second one.
  • A different AI family critiques. The arbiter refuses a same-family critic unless you override it, and the override is recorded.
  • Code runs the process. One legal next step at a time, with regressions reverted by git.
  • Any agent that can run a shell command can drive it. It is a plain CLI with exit codes and file state.
  • It measures itself. Compute-matched baselines, pass bars fixed before data, and a null result counts as an answer.

Also in the repo: an unattended goal queue (claive goal, claive serve), and stats and pick, which choose a critic from past results.

What it's built on

The idea comes from Refining Over Resampling (Bilal et al., arXiv 2608.05643): sampling more answers hits diminishing returns, so refine one first. The paper studies math reasoning. claive adapts the idea to coding agents, which the paper did not test.

The experiment

For frontier coding agents, does verifier-gated refinement, with selective breadth only when refinement stalls, beat a single run and compute-matched resampling?

A
One try.
R
Two identical tries; the tests pick.
R′
Two different setups; the tests pick.
B
Fix loop with a critic.
B0
Fix loop without a critic, from test output alone.
D
Fix loop, then a different second try only if stuck.

Each decision has a pass bar, written down before the first data run, and a null result is an acceptable outcome. The bars are still being tuned, so they are not published here yet.

Status. A small set of tasks, built from real fix commits of the author's own project. The first batch has not run. The only run so far is the shakedown above. A set this small supports exploratory conclusions only. Compute is measured in tokens and wall-clock time, not money.

Cheaper agents, same recipe

Give a cheap agent the recipe and a failing test. The loop does the checking. That is the bet the experiment tests. It is not a result.

Pi can run reviewers or second attempts on free-tier and flash-class models when those providers are available. Free-tier models can rate-limit, change, or disappear. The stats and pick commands were built by a worker running through claive's own ladder. None of this demonstrates cost savings, better results than frontier models, or local-model support.

Try it

You need Linux and Python 3 (standard library only). Muse is the default worker engine; Pi, Claude Code, and Codex are also supported with their own installation and model policies. The optional worker pane needs tmux and Codex.

New to this? All you need is a repo and one command that currently fails, such as a test. That command is your verifier.

Install

git clone https://github.com/ham-zax/claive.git && cd claive
./install.sh --dry-run   # lists what would be copied; changes nothing
./install.sh             # installs the tools and skills for Claude Code and Codex

Ask your agent

Start a new Claude Code or Codex session and say:

Use the worker-orchestration skill. You have my permission to delegate to Muse/Pi workers.
Repo: /abs/repo. Task: <goal>. Verifier: <command that fails now>. Arm D. Don't commit.

Or drive the arbiter yourself

claive-orch init --repo /abs/repo --task-file /abs/task.md --verify 'python3 -m pytest -q' --arm D
claive-orch next RUN       # prints NEXT, Why and How: do exactly that one action
claive-orch report RUN     # outcome, score trajectory, critics, tokens
claive-orch integrate RUN  # apply the winner and re-verify in your checkout

What isn't built

  • Jev-based control, so arms C and E do not exist.
  • Stuck detection inside a single turn.
  • A test-author worker for hidden checks.
  • Enforced token budgets.
  • OpenCode as a direct worker engine (Pi uses the separate opencode2api route).
